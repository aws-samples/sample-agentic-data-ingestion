# Quality Checks Creation Lambda Function

## Description
This Lambda function builds the pipeline's data quality check configuration from the approved target schema, records what the generated ETL code will actually do about quality, and assembles the payload a human sees at the first-run approval gate.

## Purpose
- Generates quality rules from the target schema of the approved field mapping
- Records a `quality_verdict` stating whether the generated Glue job's quality evaluation gates the write or only reports
- Combines infrastructure status and quality configuration into the `first_run` approval payload
- Emits the step's stage duration for the dashboard's per-stage timing

## Requirements Addressed
- Requirement 9.1: Add appropriate data quality rules when pipeline infrastructure is ready
- Requirement 9.2: Integrate quality checks into Glue job execution
- Requirement 9.3: Halt pipeline and provide detailed failure information when quality checks fail

**Read 9.2 and 9.3 against what the code does, not as a promise.** The DQDL ruleset that runs inside the Glue job is generated by `create_code`, not here; this function reads it to derive the verdict. And nothing in the pipeline halts a run on a quality result: `job_completion` closes a run on Glue job state alone. The `execution_config` keys that once implied otherwise (`fail_on_error`, `max_error_threshold` and two siblings) were removed rather than honoured, because honouring them would have meant building enforcement that does not exist. The reasoning is recorded on `create_quality_check_configuration` (`lambda_function.py:237`). The honest replacement is the `quality_verdict` record, which states the posture including `blocks_run`.

## Input
```json
{
  "run_id": "run-20241112-abc123",
  "pipeline_id": "pipeline-customer-data",
  "mapping_id": "mapping-9f2c1a..."
}
```

`run_id` and `pipeline_id` are required. `mapping_id` is optional: without it there is no target schema to read, and rule generation degrades to an empty rule set rather than failing the step.

## Processing
1. **Read the target schema** for `mapping_id` from the schema mappings table (`lambda_function.py:56`). A not-found mapping returns no schema; a throttle or access-denied raises instead of masquerading as a missing schema.
2. **Generate rules** from that schema (`:144`): per-field type checks, null checks for required fields, format checks, numeric range checks, plus a row-count and a duplicate check for the dataset. This is its own rule vocabulary and is not DQDL.
3. **Read the three code-generation facts** off this run's `create_code` state row (`:78`): the template that was rendered, the DQDL ruleset baked into the job, and whether the job opted into data quality. A read failure here is recorded in the verdict's `determined_from` rather than failing the step.
4. **Derive the `quality_verdict`** from those facts (`:407`), not from the rules generated in step 2.
5. **Assemble the `first_run` approval payload** (`:287`), combining infrastructure status from the previous step with the quality configuration and the verdict.
6. **Write the state row** under `(run_id, step_name="create_quality_checks")` with `approval_required: True`, putting `quality_verdict` and `approval` inside `output_data` so the run-detail API returns them.
7. **Record the stage duration** (`:482` on success, `:541` on failure). Recording only; it evaluates no threshold and gates nothing.

## Output
```json
{
  "statusCode": 200,
  "run_id": "run-20241112-abc123",
  "pipeline_id": "pipeline-customer-data",
  "quality_configuration": { "quality_rules": [], "rule_summary": {}, "output_config": {} },
  "total_rules": 8,
  "error_rules": 5,
  "warning_rules": 3,
  "quality_verdict": { "mode": "advisory", "blocks_run": false },
  "approval_required": true,
  "next_step": "first_run_approval"
}
```

Shape read from `lambda_function.py:516-529`; the values are illustrative. On failure the function writes a `failed` state row and raises `StepFailure` (`:589`), because returning an error payload would be treated as task success by Step Functions.

## AWS Permissions Required
- Glue: the shared Glue admin statement on `qualityChecksRole` (`foundation-stack.ts:656`), which is
  `glue:*` scoped to project-named Glue resources (`foundation-stack.ts:248-254`), not account-wide.
  The handler calls no Glue API: it constructs a Glue client at `lambda_function.py:50` and never
  uses it, so the grant is currently unexercised
- DynamoDB: read/write on the state table, read on the pipelines and schema mappings tables
- EventBridge: `events:PutEvents` on the project event buses (`foundation-stack.ts:657`)
- CloudWatch: Logs write access

## Environment Variables
Set by CDK at `compute-stack.ts:859-862`. Each falls back to the canonical table name when unset, via `os.environ.get` (`lambda_function.py:44-46`). Note that this differs from its sibling step Lambdas, which use `require_env` and so raise outside local mode instead of falling back.

- `STATE_TABLE`: pipeline state table
- `PIPELINES_TABLE`: pipelines table
- `MAPPINGS_TABLE`: schema mappings table

Declared in `deploy-cdk/lib/compute-stack.ts:849-863`: Python 3.12 on arm64, 300 s timeout (`:856`), 512 MB (`:857`), `[adotLayer, strandsLayer]` (`:858`).
