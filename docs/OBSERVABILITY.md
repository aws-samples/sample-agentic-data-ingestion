# Observability

Generic observability reference for Agentic Data Ingestion: CloudWatch Logs Insights
query recipes, error tracking, distributed tracing, and the monitoring commands used to
watch a running system.

**How this differs from [TROUBLESHOOTING.md](TROUBLESHOOTING.md).** That document is a
symptom index — you arrive holding a specific failure and look it up. This one is a
query and monitoring reference — you arrive holding a question and need the query that
answers it, whether or not anything is wrong. **A query recipe is not a symptom**, which
is why the two live apart: filed inside a symptom index, generic recipes have no symptom
to sit under and become the miscellaneous bucket at its end.

For what the system emits and why, see
[ARCHITECTURE.md § Monitoring & Observability](ARCHITECTURE.md#monitoring--observability).

## Observability & Structured Logging (Phase 8)

**Every** Lambda function emits structured JSON logs via AWS Lambda Powertools Logger — there is no exception to check for. Each log entry includes `run_id`, `pipeline_id`, and `step_name` for cross-Lambda correlation. (Function count and derivation: [ARCHITECTURE.md § System Inventory](ARCHITECTURE.md#system-inventory).)

### CloudWatch Logs Insights Queries

Run these queries in CloudWatch Logs Insights. Select all `/aws/lambda/agentic_data_ingestion_*` log groups for cross-Lambda queries.

#### Trace a full pipeline run across all Lambdas

```
fields @timestamp, step_name, level, @message
| filter run_id = "run-2026-03-03-abc123"
| sort @timestamp asc
| limit 200
```

#### Find all errors for a specific run

```
fields @timestamp, step_name, level, @message
| filter run_id = "run-2026-03-03-abc123"
| filter level = "ERROR"
| sort @timestamp asc
```

#### Find all errors across all pipelines in the last hour

```
fields @timestamp, step_name, run_id, pipeline_id, @message
| filter level = "ERROR"
| sort @timestamp desc
| limit 50
```

#### Find slow Lambda invocations (> 10 seconds)

```
filter @type = "REPORT"
| fields @requestId, @duration, @billedDuration, @memorySize, @maxMemoryUsed
| filter @duration > 10000
| sort @duration desc
| limit 20
```

#### Count invocations per step for a pipeline run

```
filter run_id = "run-2026-03-03-abc123"
| stats count(*) as log_count by step_name
| sort log_count desc
```

#### Find cold starts

```
filter @type = "REPORT"
| fields @requestId, @duration, @initDuration
| filter ispresent(@initDuration)
| sort @initDuration desc
| limit 20
```

#### Search for a specific error message pattern

```
fields @timestamp, step_name, run_id, @message
| filter @message like /AccessDenied|Unauthorized/
| sort @timestamp desc
| limit 20
```

#### Pipeline execution timeline (duration per step)

```
filter run_id = "run-2026-03-03-abc123"
| filter @message like /Processing|Starting|Completed|Failed/
| fields @timestamp, step_name, @message
| sort @timestamp asc
```

### Error Tracking

Failed pipeline steps are automatically captured in the `agentic_data_ingestion_errors` DynamoDB table by the execution updater Lambda. Errors are classified by type:

| Error Type | Pattern Matches |
|------------|----------------|
| `permission` | AccessDenied, Unauthorized |
| `timeout` | Timeout, TimedOut |
| `data_format` | JSONDecodeError, CSV, schema, parse |
| `code_error` | SyntaxError, NameError, TypeError |
| `infrastructure` | ResourceNotFound, BucketNotFound |
| `throttling` | Throttling, TooManyRequests |
| `unknown` | Default fallback |

Query recent errors:
```bash
aws dynamodb query --table-name agentic_data_ingestion_errors \
  --key-condition-expression "error_date = :d" \
  --expression-attribute-values '{":d":{"S":"2026-03-03"}}' \
  --region us-west-2
```

Errors auto-expire after 90 days via DynamoDB TTL.

### Dashboard Errors Page

The dashboard includes an Errors page at `/errors` showing recent failures across all pipelines. Features:
- Date range picker (default: last 7 days)
- Error type filter dropdown
- Columns: Date, Pipeline, Step, Error Type, Message
- Click through to the pipeline run for full context

### Distributed Tracing

OTEL traces are auto-generated by the ADOT Lambda Layer. To view traces:

1. **CloudWatch Transaction Search**: CloudWatch → Transaction Search → search by `run_id` or time range
2. **X-Ray Console**: X-Ray → Traces → filter by `service.name = agentic-data-ingestion-*`
3. **Service Map**: X-Ray → Service Map → shows all Lambda-to-service connections

### Step Logs in Dashboard

The step flow visualization shows actual log lines for each step. If logs appear empty:

1. **Check the step is completed** — logs are only fetched for completed steps
2. **Check CloudWatch Logs** — verify the Lambda log group has entries:
   ```bash
   aws logs filter-log-events \
     --log-group-name /aws/lambda/agentic_data_ingestion_file_validation \
     --filter-pattern '{ $.run_id = "*" }' \
     --limit 5 --region us-west-2
   ```
3. **Check IAM permissions** — the dashboard API Lambda needs `logs:StartQuery` and `logs:GetQueryResults`
4. **Check cache** — cached logs are stored in `agentic_data_ingestion_executions` table under `step_logs.{step_name}`

## Monitoring

```bash
# Lambda logs
aws logs tail /aws/lambda/agentic_data_ingestion_dashboard_api --follow --region us-west-2

# Step Functions execution history
aws stepfunctions get-execution-history --execution-arn <arn> --region us-west-2

# CloudWatch metrics
# Check Lambda: Duration, Errors, Throttles
# Check DynamoDB: ConsumedReadCapacity, ThrottledRequests
```
